## 5. Phase 1: 勾配累積の等価性監査

対象: commit 858a1f5 の `sokudan/train/loop.py`（`--grad-accum`）。batch 24 × 累積 1 と batch 12 × 累積 2 を比べます。

**結論: バグ 1 件（修正済み）＋仕様上の非等価 2 件。** その他の項目は等価です。

| 項目 | 結果 | 根拠（コード） |
|---|---|---|
| 損失を累積回数で割っているか | 割っている。ただし**エポック末尾の短いグループも 2 で割っていた（バグ）** | 修正前 `(loss / accum if accum > 1 else loss).backward()` → 修正後 `(loss / accum_group_size(batch_index, len(batches), accum)).backward()`（累積 1 は `loss.backward()` のまま） |
| optimizer.step と zero_grad が累積の区切りだけか | 等価 | `if first: optimizer.zero_grad(set_to_none=True)`（`first = batch_index % accum == 0`）、`if (batch_index + 1) % accum == 0 or batch_index + 1 == len(batches):` の中で `optimizer.step()` |
| スケジューラの単位、総ステップ数と warmup | 等価（optimizer のステップ単位） | `if first: apply_lr(step)`、`step += 1` は optimizer.step と同じ分岐の中。`steps_per_epoch = math.ceil(math.ceil(len(train_examples) / config.batch_size) / config.grad_accum)`。ceil(ceil(n/12)/2) = ceil(n/24) が整数について常に成り立つ。warmup は `int(total_steps * config.warmup_fraction)` で共通 |
| 勾配クリッピングが累積後に 1 回か | 等価 | `nn.utils.clip_grad_norm_(model.parameters(), config.max_grad_norm)` は optimizer.step の直前、同じ分岐の中だけ |
| エポック末尾の余り | **バグ**（上記）。 | マイクロバッチ数は base12 で 5,617、long で 6,803（どちらも奇数）。最後のグループは 1 マイクロバッチなのに ÷2 され、毎エポック 1 ステップの勾配が半分になっていた。修正後はグループの実際の数で割る（`accum_group_size`） |
| 損失の正規化の単位 | **仕様上の非等価（大きさを記録）**。 | `stage1_loss` は choice/bool の CE 平均と RPS 平均を件数で重み付けして足すので、1 マイクロバッチ内では「全行の平均」になる。RPS も 1 行ずつの値の平均（`(squared.sum(dim=1) / (k_per_row - 1.0)).mean()`）。そのため**同じ大きさの 2 つ（12 + 12）の平均の平均は 24 件の平均と一致**する（mask 位置の数や型の内訳に依らない）。一致しないのは大きさが違うとき（端数のマイクロバッチ）だけ |
| バッチの組み方 | **仕様上の非等価（意図どおり）**。 | `length_bucketed_batches` の窓は `batch_size * bucket_multiplier`（384 と 768）で、できたバッチを `rng.shuffle(batches)` で並べ替える。batch 12 の 2 つのマイクロバッチは、batch 24 の 1 バッチを 2 つに割ったものではなく、長さの近い別々の 12 件の組がランダムに対になる。乱数の消費も変わるので、同じ seed でもデータの順序は batch 24 と一致しない |

端数の具体例: 67,394 行は 24 でも 12 でも余り 2 です。

- batch 24 では、2 行のバッチが単独で 1 ステップになります。
- batch 12 では、2 行のマイクロバッチが別の 12 行のマイクロバッチと対になります。各行の重みは 1/4 で、14 行の平均なら 1/14 です。
