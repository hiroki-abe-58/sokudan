## 2. 監査の項目別の結果（`docs/noise_floor.md` §5 に全文）

| 項目 | 結果 | コード |
|---|---|---|
| 損失を累積回数で割っているか | 割っている。**ただしエポック末尾の短いグループも 2 で割っていた（バグ、修正済み）** | 修正前 `(loss / accum if accum > 1 else loss).backward()`、修正後 `(loss / accum_group_size(batch_index, len(batches), accum)).backward()`（累積 1 は `loss.backward()`） |
| step / zero_grad が区切りでだけか | 等価 | `if first: optimizer.zero_grad(set_to_none=True)`、`if (batch_index + 1) % accum == 0 or batch_index + 1 == len(batches):` の中で `optimizer.step()` |
| スケジューラの単位、総ステップ数、warmup | 等価（optimizer ステップ単位） | `if first: apply_lr(step)`、`steps_per_epoch = math.ceil(math.ceil(len(train_examples) / config.batch_size) / config.grad_accum)`（ceil(ceil(n/12)/2) = ceil(n/24)） |
| クリッピングが累積後に 1 回か | 等価 | `nn.utils.clip_grad_norm_(...)` は optimizer.step の直前、同じ分岐の中だけ |
| エポック末尾の余り | **バグ**（上記）。 | マイクロバッチ数は base12 で 5,617、long で 6,803（奇数）→ 毎エポック 1 ステップが半分の勾配だった |
| 損失の正規化の単位 | 同じ大きさのマイクロバッチなら等価。**大きさが違うと非等価（仕様）** | `stage1_loss` は件数で重み付けした全行の平均。RPS も `(squared.sum(dim=1) / (k_per_row - 1.0)).mean()`。端数の 2 行のマイクロバッチは各行の重みが 1/4 になる（14 件の平均なら 1/14） |
| バッチの組み方 | **仕様上の非等価** | `length_bucketed_batches` の窓は `batch_size * bucket_multiplier`（384 と 768）。`rng.shuffle(batches)` でマイクロバッチがランダムに対になり、乱数の消費も変わる |

   3 本で見えていた「位置が効く、断りが落ちる」は、どちらも検定を通りました。
   io_sf の M2 の平均は、v0.1 の 8 本の最大（0.8814）を上回っています（0.8821）。
