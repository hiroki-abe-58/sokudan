# 性能改善 A（数値を変えない）

2026-09-27。出発点は性能診断（`ローカルの性能診断レポート（リポジトリ外）`、2026-09-26 22:38〜23:10、観測のみ）です。

- **診断の結果**: 学習中の SM 使用率は平均 74% でした。律速は、メインスレッドで直列に走るトークナイズとバッチ組み立て、それに毎ステップの loss の同期です。
- **1 seed あたりの時間**: 825 秒（学習ループ 695 / 学習中の val 評価 66 / 外部評価 49 / 切り替え 21）。

**A は、学習と評価の数値を 1 つも変えないことが条件です。** 変えていないことは、A を入れる前のコード（commit 32435eb）で取った基準の記録と比べて確認します（§3）。

## 1. 入れたもの

| # | 内容 | 場所 | 数値が変わらない理由 |
|---|---|---|---|
| A2 | **例ごとのトークナイズ結果のキャッシュ** | `JointCollator(cache=True)`、`sokudan/train/dataset.py` | `encode_joint` は、例とコレータの設定だけで決まる純関数です。キャッシュのキーは例のオブジェクトの同一性で、同じオブジェクトかどうかも確かめます。`truncated` の数は、キャッシュから返した分も数えます |
| A1 | **バッチ組み立てをバックグラウンドのスレッドで先読み**（深さ 2） | `prefetched()`、`sokudan/train/loop.py`（学習ループと `evaluate`） | 生産者は 1 本、FIFO の 1 本のキューです。バッチの構成・順序・中身は、そのまま回した場合と同じです。スレッドは生成器を抜ける前に join するので、コレータを 2 つのスレッドから同時に使うことはありません |
| A3 | **loss の同期を間引く** | `train` の `pending` と `_flush_losses` | 各ステップの loss はデバイス上に置き、ログの行（50 ステップごと）とエポックの終わりに 1 回で読みます。`float` した値は、`float(loss.detach())` と同じ fp32 の値です |
| A5 | **val の推論の重複をなくす** | `evaluate(rows_out=...)`、`eval_local_attention.py --save-probs`、`soup_eval.collect(precomputed=...)` | 外部評価の 1 回の val の推論で、ガードレールの値と事例ごとの予測を両方とも作ります。関数、batch 32、バケット化、autocast は、`collect` が別に推論していたときと同じです。`collect` は保存した予測を写すだけで、モデルをもう一度走らせません |
| A7 | **フェーズの切り替えの空白を減らす** | `scripts/perf_run.py` | 学習プロセスの終了を `Popen.wait` で待ちます。これまでの駆動スクリプトは 5 秒おきに確認していました。終わった瞬間に評価を始めます |

## 2. 入れていないもの（理由）

| 項目 | 理由 |
|---|---|
| A4（評価のバッチサイズを変える） | padding の長さが変わると、bf16 のカーネルの選び方が変わって末尾の桁が変わりうる（診断 §4）。数値を変えない条件を満たせるかが分からない |
| A6（学習前の val 評価を省く） | 今回の指示に含まれていない。report.md と metrics.json の `before` もなくなる |
| 学習と評価を 1 プロセスにまとめる | 構造が変わるので見送り。評価プロセスの起動費（データ読み込み、モデル構築）は残る |
| `pin_memory` と `non_blocking` | 今回は入れていない（A1 のスレッドで十分か、先に測る） |
| A8〜A12（常駐プロセス、AV の除外、電源プラン、sysmem fallback、P コアへの固定） | マシンの設定の変更で、リポジトリの外。変更は指示されていない |

## 3. 同一性の確認（`tests/test_perf_identity.py`）

- **基準の記録**: A を入れる前のコード（worktree `../sokudan-preA`、commit 32435eb）で、`scripts/perf_record.py` を使って `runs/perf/pre/` に取ります。

| テスト | 内容 | 実行 |
|---|---|---|
| (a) | 決定的モードで最初の 20 ステップを走らせ、各ステップのバッチ（事例の番号）と loss（`float.hex`）が完全に一致すること | GPU |
| (b) | 2 エポック分のバッチの並びのハッシュが基準と一致し、`prefetched` がその順で渡すこと。途中で止めても、コレータの例外でも、きれいに終わること | CPU |
| (c) | キャッシュとスレッドを通したテンソルと `truncated` の数が、キャッシュなし・呼び出し元スレッドのコレータと一致すること（2 周目はキャッシュから）。同じ `id` の別オブジェクトにキャッシュを返さないこと。loss の読み出しが、ステップごとの `float` と同じ値になること | CPU |
| (d) | `eval_local_attention --save-probs` の事例ごとの予測（frozen、長文 val、val）が、基準の `collect` の予測とビット単位で一致すること。評価の出力（M1〜M4、ガードレール）が基準と一致すること | GPU |

**GPU の非決定性への対処（基準を取る前に決めておく）**:
- 基準の 20 ステップは、A を入れる前のコードで **2 回**取ります（`steps.json` と `steps_repeat.json`）。
- 2 回がビット単位で一致すれば、(a) はビット単位の一致を要求します。
- 一致しなければ、(a) の基準は「A の loss と基準の loss の差が、基準の 2 回の差の最大値以下で、バッチの並びは完全に一致」とします。
- (a) か (d) が落ちた場合は、その項目に関わる A の変更を戻します（指示どおり）。

**bf16 について（指示の Phase 3.3）**:
- 学習は、すでに bf16 autocast で動いています（`TrainConfig.amp_dtype = "bfloat16"`、v0.1 から。診断 §2.2 とコードで確認）。
- 指示の「bf16 autocast のフラグを追加する（既定は無効）」は、既定を fp32 にすることになり、既定の学習の数値を変えます。
- そのため、フラグの追加と bf16 の 1 本の計測は**行いません**。保守的な方を選びました。Phase 5 も行いません（「見送り（前提が現状と違う）」）。

結果と速度は、Phase 3 の後に §4 以降へ追記します。

# 結果（2026-09-27、Phase 3）

## 4. 同一性の確認（`runs/perf/phase3.log`）

| 段 | 時刻 | 結果 |
|---|---|---|
| 基準の記録（A を入れる前のコード、worktree 32435eb） | 02:22:32 – 02:25:28 | `steps.json`、`steps_repeat.json`、`preds.npz`、`eval.json` |
| (a)〜(d)（`SOKUDAN_TEST_GPU=1`） | 02:25:29 – 02:27:03 | **8 件すべて pass** |

- **(a)**: 基準の 2 回は、ビット単位では一致しませんでした。
  - バッチの並びは完全に一致し、loss の差は最大 1.62e-4 でした。
  - 決定的モードでも、memory-efficient attention の backward は非決定的です（torch の警告）。
  - そのため、§3 で先に決めた「基準の 2 回の差の範囲内」を基準にしました。テストの実行では、A の 20 ステップはバッチが完全に一致し、loss もその範囲内でした。
  - **記録用に取った 3 回目（A、02:27）**: バッチは完全に一致しました。loss の差は、基準 1 回目と最大 1.72e-4（範囲 1.62e-4 をわずかに超える）、基準 2 回目と最大 1.44e-4 でした。
  - GPU の非決定性と同じ桁の揺れで、A を戻す理由とは判断していません（テストの判定は pass）。
- **(d)**: 外部評価の事例ごとの予測（frozen 9,850 件、長文 val、val 12,158 件）は、基準とビット単位で一致しました。評価の出力（M1〜M4、ガードレール）も一致しました。
  - Phase 1 の旧コード 8 本の評価の途中から A が入っていましたが、この結果で、A が評価の数値を変えていないことを確認しています。
