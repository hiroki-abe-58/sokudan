## 5. 判定の根拠

- **型 B**: qf-long − qf-short = +0.024541 ≤ 0.028295（差なし）、かつ sf-short − qf-short = +0.040043 > 0.028295（差あり）。
  型 A は qf-long > qf-short が差ありでないため不成立、型 C も同じ理由で不成立。
- **最終候補 qf-short**: 足切り（M1 ≥ 0.881718、M5 ≥ 0.772710、choice ≥ 0.700911、RPS ≤ 0.187460、score acc ≥ 0.512931、
  bool acc ≥ 0.929407）を通ったのは qf-short だけ。M5 で落ちたのは sf-short 0.721798、sf-long 0.769431、qf-long 0.770407。
  qf-long は choice 0.699730 でも落ちた。

## 6. 予想と違ったこと

1. **qf-long の M2 は 3 シードとも v0.1 の最大（0.8571）を上回りました**（0.8702 / 0.8673 / 0.8713、幅 0.0040）。
   それでも事前登録の「差あり」の基準は 2 条件の幅の大きい方（ここでは v0.1 の 0.0283。v0.1 seed 1 の 0.8288 が広げている）
   なので、判定は「差なし」です。規則は動かしていません。
2. **長文を足しても state_first には何も上乗せされませんでした**（0.8851 → 0.8853）。sf-long は seed 間のばらつきが大きく
   （M2 幅 0.0379、M1 0.8598〜0.9054）、seed 1 は M1・M5 とも低い。
3. **参考値ですが、qf-long で `ends_with_question`（M3）が 0.6614 → 0.7223 に上がりました**（seed 2 は 0.6440 で、幅は 0.1296）。
   位置を変えた sf-short では上がらなかった属性です。判定には使っていません。
4. **M5 は v0.1 以外の全条件で下がりました**。qf-long（0.7704）と sf-long（0.7694）は v0.1 の最小との差がそれぞれ 0.0023、0.0033 です。
5. 長文の行（最長 875 トークン）では batch 24 がメモリ上限（0.88）に収まりませんでした。

## 7. 規則にない状況での判断（すべて保守側を選んだつもりのもの）

1. **生成の `max_tokens` 1000 → 2400**: 1000 のままでは長文の末尾が切れる（既存の長文コーパスで 8〜20%）ため、出力の上限だけを上げました。
   プロンプトは長さの指定以外変えていません。試験生成では 27/27、本生成では各バッチ 175/179 以上が文末で終わりました。
2. **メモリ不足（qf-long s0、batch 24）**: 規則にあるのは速度超過の再試行だけです。VRAM の上限を緩めることも、止めて 2×2 を
   不成立にすることもせず、事前登録された再試行の方式（batch 12 + 勾配累積 2、1 回）を **long の 6 本すべて**にそろえて適用しました。
   既定の経路（累積 1）は、変更前のコードと同じ損失の揺れの範囲にあることを確かめています。
   **short の 2 条件（batch 24）と long の 2 条件（batch 12 × 2）では、マイクロバッチの組み方も違います。** 比較の上での交絡として残ります。
3. **ollama の VRAM 上限**: 前回までに方式の記録がなかったため、`OLLAMA_GPU_OVERHEAD`（6 GiB を空ける）で起動し直しました。
   もとは常駐アプリ（ollama app.exe）が動いていましたが、終了処理では生成サーバーを残さない指示に従い、**再起動していません**。

## 8. 判断していただきたいこと

1. **bench を回すか**: 最終候補は v0.1 なので、今回の結果からは bench を回す理由はありません。
   bench_ja には 400 トークン以上の state がないため、M2 の差は bench_ja には出ません。
2. **qf-long の扱い**: 規則上は「差なし」です。ただし M2 は 3 シードとも v0.1 の最大を上回り、M1 は平均 0.8938 と 4 条件で最高です。
   足切りで落ちた理由は M5 と choice の小差（0.0023、0.0012）です。v0.1 の 3 シードの幅が大きいことが判定を決めているので、
   シードを足して幅を詰めるかどうか。
3. **次のレバーの候補**:
   - **`implies_declining` の低下を独立に扱うか。** 位置・長さのどちらの介入でも下がっており、今回の誤り分析（14 行）では手がかりがありません。
   - **メモリの交絡を外すか。** long を batch 24 で学習できる形（系列長で分けたバッチ上限など）にして、交絡を取り除く。
   - **ollama の常駐アプリを再起動するか**（止めたままです）。
